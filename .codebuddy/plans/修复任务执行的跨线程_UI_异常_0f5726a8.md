## 产品概述

修复 FileKeeper 界面端「立即执行」任务后的跨线程 UI 异常，使压缩、清理、同步任务都能正常执行并刷新列表。

## 核心功能

- 点击「执行」或「立即执行全部」后，任务正常跑完并弹出结果汇总，不再出现「该类型的 CollectionView 不支持从调度程序线程以外的线程对其 SourceCollection 进行的更改」异常
- 任务总览列表在执行完成后正确刷新（上次执行时间、下次排期）
- 托盘菜单「立即执行全部」、编辑页「测试执行」、同步编辑页「测试连接」、设置页服务操作等所有经过 await 的路径同样不再有跨线程隐患
- 执行期间进度条与「正在执行」文案正常更新，界面不卡顿

## 边界

- 只改界面端 `FileKeeper.App`；Core / Service / Setup 无 UI 上下文，不改动
- 日志页的 DispatcherTimer 自动刷新、配置文件热重载回调（已用 UiDispatcher 保护）属于正确实现，保持不动

## 技术栈

- WPF + .NET 8（CommunityToolkit.Mvvm），沿用现有工程结构，不引入新依赖

## 根因（已勘探确认）

`TasksViewModel.ExecuteAsync` 链路中三处 `await ...ConfigureAwait(false)`（第 199、222、269 行）把后续代码切到线程池线程；finally 块的 `Refresh()`（第 296 行）经 `Rebuild`（第 375–385 行）对已绑定到 ItemsControl 的 `ObservableCollection` 执行 `Clear()/Add()`，WPF CollectionView 因此抛出截图中的异常。「发生未处理的异常」弹窗只是全局异常处理器的呈现层。

## 实现方案

1. **移除 UI 工程内全部 11 处 `ConfigureAwait(false)`**：WPF 界面工程中 await 的默认行为就是恢复到 UI 线程（DispatcherSynchronizationContext），这是安全默认；`ConfigureAwait(false)` 仅适用于无 UI 上下文的库代码。涉及文件与位置：

- `ViewModels/TasksViewModel.cs`（199、222、269，核心崩溃点）
- `ViewModels/MainViewModel.cs`（96，后续 `ServiceStatus.Refresh()`）
- `App.xaml.cs`（127，托盘执行入口，catch 中含弹窗）
- `ViewModels/TaskEditorViewModelBase.cs`（115，后续 `ReportResult` 弹窗）
- `ViewModels/SyncTaskEditViewModel.cs`（235、240，后续结果弹窗）
- `ViewModels/SettingsViewModel.cs`（160，后续 `_dialogs.ShowMessage` 与 `_statusMonitor.Refresh()`）
- `ViewModels/CleanupTaskEditViewModel.cs`（201，后续弹窗）

2. **不卡界面的依据**：任务执行本体 `TaskExecutionService.RunAsync` 走 Core 的异步 IO（7z 进程、文件、网络），await 期间不占 UI 线程；设置页的阻塞型服务操作已经用 `Task.Run` 包装，去掉 ConfigureAwait(false) 只改变「续体在哪恢复」，不改变「工作在哪执行」
3. **性能与可靠性**：无额外开销；异常从根上消除而非在 UiDispatcher 里打补丁，行为与既有 `OnExternalChanged` 的 UiDispatcher 保护路径一致、互不冲突

## 验证方式

实机回归（桌面被 IDE WebView 遮挡，沿用既有 PrintWindow 截图 + SetForegroundWindow + TAB/空格键盘导航 + UIA 断言的方式）：启动 App → 导航到任务总览 → 触发压缩任务执行 → 截图确认无异常弹窗、出现结果汇总、列表刷新正常；再触发「立即执行全部」复核托盘链路。全程 `dotnet build` 保持 0 警告 / 0 错误。
